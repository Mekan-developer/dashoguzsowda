# /commit — коммиты по логическим группам

Уточнение пользователя: **$ARGUMENTS**
(пусто — работать со всеми незакоммиченными изменениями; если указана область —
коммитить только её, остальное оставить в рабочем дереве нетронутым)

## Текущее состояние

Ветка: !`git rev-parse --abbrev-ref HEAD`

Статус: !`git status --porcelain=v1`

Объём правок: !`git diff HEAD --stat`

Последние сообщения для сверки стиля: !`git log --format='%s' -10`

---

## Что сделать

### 1. Прочитать изменения, а не только их имена

Просмотреть `git diff HEAD` (для untracked-файлов — `git diff --no-index /dev/null <файл>`
или прочитать файл целиком). Большой diff читать по каталогам:
`git diff HEAD -- <путь>`. Бинарные и сгенерированные файлы (`*.zip`, `public/build/**`,
`*.lock`) — по факту наличия, без вычитывания.

Понять по каждому куску: **что поменялось** и **почему это понадобилось** — какая
проблема решается, что было не так до этого. Если из diff-а причина не читается,
посмотреть окружающий код и связанные файлы. Не выдумывать мотивировку, которой нет.

### 2. Разбить на логические группы

Одна группа = одно смысловое изменение, которое имеет смысл откатывать целиком.
Признаки того, что это **разные** коммиты:

- разные подсистемы (docker / API / админка / мобильные доки / socket-server);
- фикс бага и рефакторинг рядом — врозь;
- удаление отжившего (scribe, старые артефакты) и добавление нового — врозь;
- правка кода и не связанная с ней правка документации — врозь.

Признаки того, что это **один** коммит: изменения не работают друг без друга
(миграция + модель + репозиторий одной сущности; переименование и все его вызовы;
новая зависимость в `composer.json` и код, который её использует — вместе с
`composer.lock`).

Порядок коммитов выбрать так, чтобы каждый оставлял репозиторий в рабочем состоянии.

Если пользователь попросил «одним коммитом» — не дробить, но в теле перечислить
логические части.

### 3. Сформулировать сообщение

Формат — как в истории проекта: Conventional Commits, **текст по-русски**.

```
тип(область): что изменилось, в повелительном наклонении, до 72 символов

Почему это понадобилось: что было не так, чем это мешало. 2–5 строк,
перенос по ~76 символов. Для тривиальных правок тело не нужно.

- путь/к/файлу — что именно в нём сделано и зачем;
- второй файл — то же самое;
- третий файл — то же самое.

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

Типы: `feat`, `fix`, `refactor`, `docs`, `build`, `chore`, `test`, `perf`, `style`.
Области из истории: `docker`, `socket`, `bruno`, `api`, `admin` — брать существующую,
если подходит.

Правила заголовка:
- по делу: «понятная диагностика, когда redis.so не загрузился», а не «правки докера»;
- без точки в конце, без «добавлены», «исправлено» — повелительное наклонение;
- не пересказывать `git status`: «изменены 5 файлов» — не сообщение.

Тело отвечает на «почему», а не на «что» — «что» видно из diff-а. Буллеты по файлам
нужны, когда коммит трогает несколько мест и по каждому есть что пояснить.

### 4. Проверить перед коммитом

Остановиться и **спросить пользователя**, если в изменениях:

- секреты: `.env`, приватные ключи, сертификаты, токены, пароли, service-account JSON
  (в этом проекте — `docker/caddy/certs/**`, `storage/app/firebase/**`, `docker/db.env`);
- отладочный мусор: `dd()`, `dump()`, `var_dump()`, `console.log`, закомментированный код,
  `Log::debug` со свежими правками;
- файлы, которые скорее должны быть в `.gitignore`, чем в индексе.

Проверить `git check-ignore` для сомнительных путей — вдруг файл уже игнорируется.

Если HEAD на `main` — не коммитить туда: сказать об этом и предложить создать ветку.

### 5. Закоммитить

По одной группе за раз:

```bash
git add <явные пути этой группы>   # без `git add -A` и без `git add .`
git status --porcelain              # убедиться, что в индексе ровно то, что нужно
git commit -m "$(cat <<'EOF'
...сообщение...
EOF
)"
```

Пути перечислять явно — иначе в коммит утекут чужие изменения. Для удалённых файлов
`git add` тоже подходит (фиксирует удаление); при массовом удалении удобнее
`git add -u -- <каталог>`.

После всех коммитов показать `git log --format='%h %s' -<число созданных коммитов>`
и `git status --short` — что осталось незакоммиченным и почему.

### 6. Не делать

- не пушить и не создавать PR — только коммиты;
- не менять код «заодно», чтобы линтер был доволен: коммитить то, что есть;
- не трогать чужие незакоммиченные изменения вне запрошенной области;
- не делать `git commit --amend` и не переписывать уже существующие коммиты;
- не добавлять `--no-verify` — если сработал хук, показать вывод пользователю.
