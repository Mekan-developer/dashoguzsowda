# Задача: подключить систему магазинов

Ты работаешь во Flutter-приложении доски объявлений (Sowda). Бэкенд — Laravel,
эндпоинты уже готовы и работают. Нужно подключить магазины для двух ролей:
**покупатель** (смотрит магазины и товары) и **владелец магазина** (заводит
магазин, выкладывает товары, следит за модерацией и тарифом).

## Базовые вещи

- **Base URL:** `https://dashoguzsowda.com.tm/api`, префикс `/v1/...`
- **Auth:** `Authorization: Bearer {token}` — для всего под «владелец» и для тарифов.
  Публичные GET-эндпоинты магазинов работают без токена.
- **Locale:** заголовок `Accept-Language: tk` или `ru` — уже используется в проекте.
- **Именование полей:** `snake_case`.
- **URL изображений:** может прийти относительным (`/storage/...`) — резолвить через origin API.
- Форматы ответов, ошибок и пагинации — те же, что уже используются в приложении.

## Главные правила логики — прочитай до того, как писать код

### 1. Товар магазина — это объявление, а не отдельная сущность

На бэкенде **нет** модели `Product`. Товар магазина — обычное объявление
(`Listing`) с непустым полем `store` и торговыми полями. **Не создавай отдельную
модель Product** — расширь существующую модель `Listing`:

```dart
// добавить в существующий Listing
final double? price;            // розничная цена (уже есть)
final double? wholesalePrice;   // оптовая цена за единицу
final int? minOrderQty;         // минимальная партия для опта
final int? stockQty;            // остаток, см. правило 4
final StoreBrief? store;        // null у обычного объявления
final GeoRef? district;         // район, может быть null
```

Из этого следует: карточка товара, избранное, жалобы, поиск и загрузка фото
у товаров магазина — **те же самые экраны и тот же код**, что у обычных
объявлений. Ничего дублировать не нужно.

### 2. Опт и розница — два независимых флага, не enum

У магазина `sells_retail` и `sells_wholesale` — оба `bool`, и **оба могут быть
`true` одновременно**: «оптом и в розницу» — обычный режим работы. Не заводи
`enum StoreType { retail, wholesale }`.

На карточке магазина:
- только `sells_retail` → плашка «Розница»
- только `sells_wholesale` → плашка «Опт»
- оба → «Опт и розница» (или обе плашки рядом)

У товара то же самое, но по ценам: `price` и `wholesale_price` независимы.
Показывай ту плашку, у которой цена не `null` — товар может иметь обе.

### 2a. Опт видит не каждый — это цепочка «клиент → розничный продавец → оптовик»

Оптовое предложение сервер показывает **только владельцу одобренного и
активного розничного магазина**. Обычный покупатель и гость опта не видят
вообще, и фильтровать на клиенте **ничего не нужно** — бэкенд отсекает сам:

- `wholesale_price` и `min_order_qty` приходят `null`;
- `sells_wholesale` приходит `false`, даже если магазин торгует оптом;
- чисто оптового магазина (`sells_retail == false`) нет в `/v1/stores`
  и `/v1/stores/popular`, его карточка и товары отдают `404`;
- `type=wholesale` и `trade=wholesale` возвращают **пустой список**;
- заказать оптовое предложение нельзя — `422`.

Из этого следует практическое: **переключатель «Опт» на экране магазинов
показывай только тогда, когда пользователь опт видит** — иначе он нажмёт
и получит пустой экран. Признак — есть свой магазин с `sells_retail == true`
и `status == approved` (данные уже в профиле, отдельный запрос не нужен).
Свои товары и свой магазин владелец видит всегда, с оптом.

### 3. Доставка — только флаг, цены доставки в системе нет

`has_delivery: true` → показать иконку доставки и текст «Доставка».
`has_delivery: false` → «Самовывоз, оплата на месте».

**Стоимость и сроки доставки бэкенд не считает и не хранит** — покупатель
и владелец созваниваются по телефону магазина и договариваются сами. Не рисуй
поле «стоимость доставки» и не проси её у API, её нет.

### 4. Наличие: одно поле `stock_qty` на три состояния

| Значение | Что показать | Кнопка заказа |
|---|---|---|
| `null` | «В наличии» | активна |
| `0` | «Нет в наличии» | неактивна |
| `N` | «В наличии: N шт» | активна |

`null` означает «владелец не ведёт учёт», а не «неизвестно». Не путай с `0`.
Когда появится корзина, она будет уменьшать это же поле — закладывайся на это.

### 4a. Способы оплаты — справочник сервера, не enum

У магазина есть `payment_methods: [{ id, name_tk, name_ru }]` — чем с ним можно
рассчитаться. Минимум один элемент есть всегда.

Это **единственное место, где бэкенд отдаёт текст, а не флаг**: список ведёт
админ и может пополнить его в любой момент, поэтому названия приходят готовыми
на двух языках. **Не заводи enum и не зашивай варианты** — рисуй то, что пришло,
подпись бери по текущей локали (`name_tk` / `name_ru`).

Онлайн-оплаты в приложении нет: деньги продавец получает сам при доставке, это
только договорённость о способе расчёта.

### 5. Все тексты и иконки рисует приложение

Бэкенд **не отдаёт** строк «Розница», «Опт», «Самовывоз, оплата на месте»
и не отдаёт эмодзи. Он отдаёт только флаги и числа. Все подписи бери
из локализации приложения (tk/ru), как и остальной UI.

### 6. Магазин доступен только на тарифе с правом на магазин

Проверяй **`can_have_store`** из каталога тарифов или профиля.
**Не сравнивай `name == "Premium"`** — набор тарифов меняется из админки.

### 7. Тариф оплачивается наличными администратору, а не онлайн

`PUT /v1/profile/subscription` **не выдаёт платный тариф**. Он создаёт заявку
и отвечает **202**. Тариф включает администратор после того, как получит деньги.
Подробности — в разделе про экран тарифа.

## Эндпоинты

### Публичные (покупатель, токен не нужен)

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/v1/stores` | Список магазинов с фильтрами |
| `GET` | `/v1/stores/popular` | Витрина на главной (курируется админкой) |
| `GET` | `/v1/stores/{id}` | Карточка магазина |
| `GET` | `/v1/stores/{id}/listings` | Товары магазина |

**`GET /v1/stores` — query:**
`type` (`retail`\|`wholesale`), `has_delivery` (0\|1), `region_id`, `city_id`,
`district_id`, `category_id`, `search`, `page`, `limit` (1–50, дефолт 20).

Важно: `type=retail` вернёт и магазины «оптом и в розницу» — флаги независимы.

**`GET /v1/stores/{id}/listings` — query:**
`trade` (`retail`\|`wholesale`), `in_stock` (1 прячет `stock_qty == 0`),
`search`, `category_id`, `sort` (`latest`\|`price_asc`\|`price_desc`), `page`, `limit`.

**Ответ Store:**

```json
{
  "id": 1,
  "name": "Altyn Bazar",
  "description": "Optom we bölek",
  "phone": "+99361234567",
  "subtitle_tk": "Azyk", "subtitle_ru": "Продукты", "subtitle": "Продукты",
  "category_id": 5,
  "sells_retail": true,
  "sells_wholesale": true,
  "has_delivery": true,
  "payment_methods": [
    { "id": 1, "name_tk": "Alanyňda nagt", "name_ru": "Наличные при получении" },
    { "id": 3, "name_tk": "Eltip berlende terminal", "name_ru": "Терминал при доставке" }
  ],
  "address": "Напротив рынка",
  "region":   { "id": 1, "name_tk": "Ahal",  "name_ru": "Ахал" },
  "city":     { "id": 2, "name_tk": "Änew",  "name_ru": "Анау" },
  "district": { "id": 3, "name_tk": "Merkez","name_ru": "Центр" },
  "logo_url": "/storage/stores/1/logo.webp",
  "photos": ["/storage/stores/1/photos/1.webp"],
  "photo_urls": ["/storage/stores/1/photos/1.webp"]

```

`photos` и `photo_urls` — одно и то же, бери любое. `district` может быть `null`.

**404 на карточке — это нормальный сценарий.** Магазин, не прошедший модерацию,
или с истёкшим тарифом владельца публично не существует. Обрабатывай как
«магазин недоступен», не как ошибку сети.

### Свой магазин (владелец, нужен токен)

| Метод | URL | Ответ |
|---|---|---|
| `GET` | `/v1/my/store` | `200`, либо `404` если магазина ещё нет |
| `POST` | `/v1/my/store` | `201`, магазин в статусе `pending` |
| `PUT` | `/v1/my/store` | `200` |
| `DELETE` | `/v1/my/store/photos/{id}` | `200` |

Один магазин на пользователя — поэтому в URL нет `id`.

**Тело (multipart).** Файлы отправляй как `POST` с полем `_method=PUT` —
так же, как в приложении уже сделано для объявлений.

| Поле | При создании | Примечание |
|---|---|---|
| `name` | обязательно | |
| `phone` | обязательно | строго `+993` и 8 цифр |
| `region_id` | обязательно | |
| `city_id` | обязательно | должен принадлежать региону |
| `district_id` | нет | должен принадлежать городу |
| `category_id` | нет | из `/v1/categories` |
| `description` | нет | до 2000 символов, одноязычное — владелец пишет на своём языке |
| `address` | нет | ориентир строкой, до 255 |
| `sells_retail` / `sells_wholesale` | нет | хотя бы один должен быть `true` |
| `has_delivery` | нет | |
| `payment_method_ids[]` | нет | id из справочника. Не прислать — при создании подставится способ по умолчанию, при правке набор не изменится. Пустой массив прислать нельзя: `422`, хотя бы один обязан остаться |
| `logo` | нет | квадрат, конвертируется в WebP на сервере |
| `photos[]` | нет | до 6 фото в галерее суммарно |

**Ответ MyStore** = Store + поля владельца:

```json
{
  "status": "pending",
  "is_active": true,
  "commission_percent": 5,
  "rejection_reason": { "id": 2, "name_tk": "...", "name_ru": "..." }
}
```

- `status`: `pending` | `approved` | `rejected` — в витрине магазин только при `approved`
- `commission_percent` — комиссия платформы с каждого проданного товара, `0` —
  комиссии нет. **Только для чтения**: ставку задаёт админ, у каждого магазина
  своя. Удерживается с магазина, покупатель платит полную сумму
- `is_active: false` — тариф с правом на магазин истёк, витрина погашена.
  Магазин сохранён, товары остались обычными объявлениями
- `rejection_reason` — приходит при `status == rejected`

### Тарифы

| Метод | URL | Что важно |
|---|---|---|
| `GET` | `/v1/tariffs` | каждый план отдаёт `price` и `can_have_store` |
| `PUT` | `/v1/profile/subscription` | `{ "tariff_name": "Premium" }` |
| `GET` | `/v1/profile` | `store` и `tariff_request` внутри |

**`PUT /v1/profile/subscription` возвращает два разных кода:**

| Код | Когда | Что делать |
|---|---|---|
| `202` | Платный тариф | Создана заявка. Показать «Заявка отправлена, оплатите администратору». Тариф ещё **не** включён |
| `200` | Бесплатный тариф | Назначен сразу |

`data` в обоих случаях — профиль целиком.

**`tariff_request` в профиле:**

```json
{
  "id": 7,
  "tariff_name": "Premium",
  "amount": 250,
  "status": "pending",
  "comment": null,
  "created_at": "2026-08-28T10:00:00Z",
  "processed_at": null
}
```

## Экраны и флоу

### Покупатель

**1. Список магазинов**

Фильтры сверху: переключатель «Все / Розница / Опт», чекбокс «С доставкой»,
регион-город, поиск. Всё уходит в query `GET /v1/stores`.

Карточка в списке: логотип, название, подзаголовок (`subtitle` — уже
локализован сервером по `Accept-Language`), плашки типа торговли, иконка
доставки, город.

**2. Карточка магазина** — `GET /v1/stores/{id}`

Сверху: логотип, название, **тип торговли крупно** (это главный признак
магазина), галерея `photos`. Дальше: описание, адрес (`region` → `city` →
`district` → `address` строкой), кнопка звонка на `phone`.

Блок условий покупки:
- `has_delivery == true` → иконка доставки + «Доставка» + подсказка, что
  стоимость и сроки обсуждаются с продавцом по телефону
- `has_delivery == false` → иконка магазина + «Самовывоз, оплата на месте»

Ниже — список товаров: `GET /v1/stores/{id}/listings`.

**3. Товары магазина**

Если у магазина оба флага торговли — дай переключатель «Розница / Опт»,
он уходит в `trade`. Чекбокс «Только в наличии» → `in_stock=1`.

Карточка товара:
- есть `price` → цена с пометкой «Розница»
- есть `wholesale_price` → цена с пометкой «Опт» + «от {min_order_qty} шт»
- есть обе → показывай обе строки
- наличие — по правилу 4
- условия доставки — из блока `store` внутри товара, чтобы не тянуть магазин
  отдельным запросом

**4. Обычное объявление vs товар магазина**

Одна и та же карточка объявления. Если `store != null` — дорисовываешь блок
магазина (логотип, название, кликабельно в карточку магазина) и торговые поля.
Если `store == null` — старое поведение без изменений.

### Владелец магазина

**Флоу целиком:**

```
Нет тарифа с can_have_store
   → экран «Магазин доступен на тарифе X» + кнопка «Оформить»
   → PUT /v1/profile/subscription → 202
   → «Заявка отправлена. Передайте {amount} администратору»
   → пока tariff_request.status == pending — показывать статус, кнопку скрыть
   → админ подтвердил → в профиле tariff обновился, can_have_store == true
        (и придёт push «Тариф активирован»)

Тариф есть, магазина нет (GET /v1/my/store → 404)
   → экран «Создать магазин» → форма → POST /v1/my/store → 201
   → status = pending: «Магазин на модерации»

Магазин есть
   → status == approved  → «Опубликован», кнопка «Смотреть в витрине»
   → status == pending   → «На модерации», правка доступна
   → status == rejected  → показать rejection_reason + «Исправить и отправить снова»
   → is_active == false  → «Тариф истёк, магазин скрыт от покупателей»
                           (не удалён — объясни это пользователю явно)
```

**Форма магазина.** Регион → город → район — зависимые селекты из
`GET /v1/regions` (город фильтруется по региону, район по городу; сервер
это проверяет и вернёт 422). Телефон — маска `+993 XX XXXXXX`. Тип торговли —
два чекбокса, оба снять нельзя. Доставка — один переключатель, без полей цены.
Способы оплаты — чекбоксы по `payment_methods` (список бери из своего магазина,
у нового — из любого чужого), снять все нельзя.

**Важное про перемодерацию:** правка `name`, `description`, `address` или
логотипа возвращает магазин в `pending` — предупреди пользователя до сохранения.
Правка телефона, типа торговли и доставки статус не меняет, магазин остаётся
опубликованным. Ориентируйся на `status` в ответе, а не угадывай.

**Создание товара.** Это существующая форма объявления плюс блок «Товар магазина»,
который показывается, только если у пользователя есть магазин:
- поля опта (`wholesale_price`, `min_order_qty`) показывай **только если
  `store.sells_wholesale == true`** — иначе сервер вернёт 422
- `min_order_qty` обязателен, если заполнена оптовая цена
- `stock_qty` — необязательное поле «Количество», с подсказкой «оставьте
  пустым, если не ведёте учёт»
- **адрес у товара магазина не спрашивай** — сервер подставит адрес магазина
  и перезапишет то, что пришло. Показывай адрес магазина как есть, только
  для чтения

## Обработка ошибок

| Код | Где | Что показать |
|---|---|---|
| `403` | `POST/PUT /v1/my/store` | «Магазин доступен только на тарифе с этим правом» → ведёт на экран тарифа |
| `404` | `GET /v1/my/store` | Не ошибка: магазина ещё нет → экран создания |
| `404` | `GET /v1/stores/{id}` | Магазин недоступен (не прошёл модерацию или скрыт) |
| `422` | `POST /v1/my/store` | Магазин уже есть — открыть существующий |
| `422` | форма магазина | Ошибки по полям в `errors`: `sells_retail` (сняты оба флага), `payment_method_ids` (сняты все способы оплаты), `phone`, `city_id`, `district_id` |
| `422` | форма товара | `wholesale_price` (у магазина нет опта), `min_order_qty` (не указан вместе с оптовой ценой) |
| `422` | смена тарифа | Уже есть незакрытая заявка — показать её статус |

Тексты ошибок приходят локализованными в `message` / `errors` по
`Accept-Language` — можно показывать как есть.

## Push-уведомления

Появились два новых `type` в payload:

| `type` | `id` | Куда вести |
|---|---|---|
| `store` | id магазина | Экран своего магазина (статус модерации) |
| `tariff` | id тарифа | Экран тарифа / статус заявки |

Сейчас неизвестный `type` уводит на `/home` — это рабочий fallback, но лучше
добавить обработку: пуши приходят на одобрение и отклонение магазина,
на подтверждение и отказ по заявке на тариф.

## Чего делать не нужно

- Не создавай модель `Product` и отдельные экраны товаров — это `Listing`
- Не делай `enum` для типа магазина — это два независимых `bool`
