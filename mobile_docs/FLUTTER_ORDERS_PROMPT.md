# Задача: подключить корзину и заказы

Ты работаешь во Flutter-приложении доски объявлений (Sowda). Бэкенд — Laravel,
эндпоинты заказов уже готовы, работают и покрыты тестами. Нужно собрать три вещи:
**корзину** (локальную), **экраны заказов покупателя** и **вкладку «Заказы»
у владельца магазина**.

## Базовые вещи

- **Base URL:** `https://dashoguzsowda.com.tm/api`, префикс `/v1/...`
- **Auth:** `Authorization: Bearer {token}` — все эндпоинты заказов требуют токен.
- **Locale:** заголовок `Accept-Language: tk` или `ru` — уже используется в проекте.
- **Именование полей:** `snake_case`.
- Форматы ответов, ошибок и пагинации — те же, что уже используются в приложении.
- Структура слоёв — как у магазинов: `orders_remote_data_source.dart`,
  `order_mapper.dart`, `api_orders_repository.dart` и отдельные cubit-ы.

## Главные правила логики — прочитай до того, как писать код

### 1. Корзина живёт на устройстве, API корзины нет

На бэкенде **нет** эндпоинтов `/v1/cart` и не будет. Корзина хранится локально
в SharedPreferences (`keyCart`), как и планировалось. На сервер она уезжает
один раз — целиком, в момент оформления заказа.

Что хранить в локальной позиции корзины:

```dart
class CartItem {
  final int listingId;
  final int qty;
  // снимок для отрисовки корзины без запроса к API:
  final String title;
  final double unitPrice;   // цена, которую видел пользователь
  final String? photoUrl;
  final int? storeId;       // чтобы группировать корзину по магазинам
  final String? storeName;
}
```

Снимок нужен только для показа. **Итоговую сумму считает сервер** — не считай
свою сумму источником истины, показывай `total` из ответа на оформление.

### 2. Заказать можно только товар магазина с доставкой

Кнопка «В корзину» показывается **только** когда у товара `is_orderable == true`.
Это готовый флаг из `ListingResource`, он уже учитывает всё сразу: товар одобрен,
магазин опубликован, у магазина `has_delivery`, товар в наличии, цена указана.

**Не собирай это правило заново** из `store.has_delivery`, `status` и `stock_qty` —
получишь расхождение с сервером. Флаг приходит в ленте, в карточке товара
и в выдаче товаров магазина.

У товаров без доставки всё как раньше: телефон продавца, звонок, договорённость.

### 3. Оптовая цена включается сама

Правило: если у товара есть `wholesale_price` и `qty >= min_order_qty` — позиция
считается по оптовой цене, иначе по `price`.

Считай это на клиенте **только чтобы показать цену в корзине**. Сервер посчитает
заново и вернёт в позиции заказа `unit_price` и `is_wholesale` — показывай их.

Крайний случай: у товара есть только `wholesale_price`, а `price == null`. Тогда
заказ на количество меньше `min_order_qty` сервер отобьёт с 422. Подставляй
`min_order_qty` как стартовое количество для таких товаров.

### 4. Оформление заказа ничего не резервирует

Остаток (`stock_qty`) списывается не при оформлении, а когда **продавец примет
заказ**. До этого товар доступен всем остальным.

Из этого следует: 422 «осталось 3 шт.» — нормальная ситуация даже для товара,
который лежал в корзине со вчера. Обработай это как рабочий сценарий, а не как
сбой: покажи текст ошибки и дай поправить количество.

### 5. Один заказ — один магазин

Заказать в один момент у нескольких продавцов **нельзя**: заказ идёт прямо
владельцу магазина, и везёт его он сам. Корзину по магазинам делит приложение:
своя секция, своя сумма и своя кнопка «Оформить» у каждого магазина, а
`POST /v1/orders` уходит **отдельно на каждый магазин**.

Если в один запрос попадут товары двух магазинов — `422` с текстом
«В одном заказе может быть товар только одного магазина…».

`stores[]` в ответе остался массивом ради совместимости, но в нём **всегда один
элемент**. **Важно:** `stores[0].id` — это id **части** заказа. Именно он идёт
в эндпоинты владельца (`accept` / `decline` / `complete`), а не id самого
заказа. Перепутаешь — 404.

### 6. Порядок: всё решает продавец

Оплаты в приложении нет — деньги при доставке, как и за тариф. Порядок такой:
покупатель оформил → заказ сразу ушёл владельцу магазина → владелец принял
(или отказался) → он же отвёз и отметил «доставлено». Админ в этом не
участвует. Поэтому:

- покупатель может отменить заказ **только пока `can_cancel == true`**
  (то есть пока продавец не ответил), дальше — 422 и звонок продавцу;
- владелец магазина отвечает **один раз**: после ответа `can_respond`
  становится `false`, а после «Принять» появляется `can_complete`;
- покупателю показываем телефон продавца (`stores[0].store.phone`) — все
  вопросы по заказу решаются напрямую с ним;
- никаких экранов «связаться с курьером», «оплатить», «трек-номер» — их нет.

### 6a. Способ оплаты — необязательный выбор из набора магазина

При оформлении покупатель может сказать, чем рассчитается: `payment_method_id`
в теле `POST /v1/orders`. Поле **необязательное** — не прислал, значит
«договорятся по телефону», заказ создастся как и раньше.

Выбор берётся **только из `payment_methods` того магазина**, чью корзину
оформляем (`GET /v1/stores/{id}` → `data.payment_methods`; магазин у заказа
один, так что набор однозначен). Чужой или выключенный способ — `422` по
`errors.payment_method_id`.

Это не платёж: онлайн-оплаты в приложении нет, деньги продавец получает сам при
доставке. Названия приходят с сервера на двух языках — enum не заводи, рисуй
что пришло.

В карточке заказа приходит обратно объектом `payment_method` — и покупателю,
и продавцу. `null` — способ не выбирали.

### 7. Тексты статусов рисует приложение

Бэкенд отдаёт только коды статусов. Подписи («Ожидает подтверждения»,
«Собирается», «Доставлен») бери из локализации приложения (tk/ru), как весь UI.

Тексты **ошибок**, наоборот, приходят с сервера уже переведёнными — их показывай
как есть, не подменяй своими.

## Статусы

### Заказ (`order.status`)

| Код | Что произошло | Что видит покупатель |
|---|---|---|
| `pending` | Оформлен, ждём ответа продавца | «Ожидает подтверждения», доступна отмена |
| `approved` | Продавец принял заказ и везёт | «Подтверждён» |
| `completed` | Доставлен, деньги получены | «Доставлен» |
| `rejected` | Продавец отказался, причина в `decision_comment` | «Отклонён» + причина |
| `canceled` | Отменён покупателем | «Отменён» |

### Часть заказа по магазину (`stores[].status`)

| Код | Что означает |
|---|---|
| `pending` | Владелец магазина ещё не ответил |
| `accepted` | Товар есть, продавец взял заказ |
| `declined` | Продавец отказался, заказ закрыт |
| `canceled` | Покупатель отменил заказ раньше, чем продавец ответил |

## Модели

```dart
class Order {
  final int id;
  final String number;          // «000017» — номер для разговора с продавцом
  final String status;
  final double total;
  final String? contactName;
  final String phone;
  final String address;
  final GeoRef? region, city, district;
  final String? comment;          // комментарий покупателя
  final PaymentMethod? paymentMethod; // чем рассчитается, null — не выбран
  final String? decisionComment;  // причина отказа продавца
  final bool canCancel;
  final List<OrderStorePart> stores;  // всегда один элемент
  final DateTime createdAt;
  final DateTime? decidedAt;
}

class OrderStorePart {           // блок stores[] в ответе
  final int id;                  // id ЧАСТИ заказа, не заказа
  final String status;
  final double subtotal;
  final String? comment;         // комментарий владельца магазина
  final StoreBrief? store;       // id, name, phone, logo_url
  final List<OrderItem> items;
}

class OrderItem {
  final int id;
  final int? listingId;          // null, если объявление удалили
  final String title;            // снимок названия на момент заказа
  final double unitPrice;        // снимок цены
  final bool isWholesale;
  final int qty;
  final double total;
  final String? photo;
}

class StoreOrder {               // то же, но глазами владельца магазина
  final int id;                  // id части заказа
  final String? orderNumber;
  final String? orderStatus;
  final String status;
  final double subtotal;
  // Комиссия платформы: ставку задаёт админ, у каждого магазина своя и
  // фиксируется на момент заказа. Удерживается с магазина — покупатель
  // платит subtotal целиком, магазину остаётся payout = subtotal − commission
  final double commissionPercent;
  final double commission;
  final double payout;
  final String? comment;
  final bool canRespond;         // показывать ли кнопки «Принять» / «Отказать»
  final bool canComplete;        // показывать ли кнопку «Доставлено»
  // Кому и куда везти — приходит сразу, ещё до ответа продавца
  final OrderBuyer? buyer;       // name, phone
  final OrderDelivery? delivery; // address, region, city, district, comment
  // Чем покупатель обещал рассчитаться — продавец едет за деньгами сам
  final PaymentMethod? paymentMethod;
  final List<StoreOrderItem> items;
  final DateTime createdAt;
  final DateTime? respondedAt;
}

class PaymentMethod {            // справочник сервера, не enum
  final int id;
  final String nameTk;
  final String nameRu;
}

class StoreOrderItem extends OrderItem {  // позиция в заказе владельца магазина
  final double commission;       // комиссия платформы с этой позиции
  final double payout;           // total − commission
}
```

## Эндпоинты

### Покупатель

#### `POST /v1/orders` — оформить заказ

```json
{
  "items": [
    { "listing_id": 108, "qty": 2 },
    { "listing_id": 251, "qty": 5 }
  ],
  "address": "ул. Магтымгулы, 12, кв. 5",
  "contact_name": "Merdan",
  "phone": "+99361123456",
  "region_id": 1,
  "city_id": 4,
  "district_id": 9,
  "comment": "Позвонить за час",
  "payment_method_id": 3
}
```

- Обязательные: `items` (до 50 разных товаров), `address` — заказ существует
  только с доставкой.
- `payment_method_id` — необязателен, только id из `payment_methods` этого
  магазина. Пусто = «договорятся по телефону».
- Необязательные: `contact_name`, `phone`, `region_id`, `city_id`, `district_id` —
  пусто означает «взять из профиля». Отправляй их, только если пользователь
  поправил данные: заказать можно и на другого человека.
- Повторы одного `listing_id` сервер сложит по количеству — но лучше
  схлопывай их в корзине сам.

Ответ `201`:

```json
{
  "data": {
    "id": 17,
    "number": "000017",
    "status": "pending",
    "total": 350,
    "can_cancel": true,
    "payment_method": { "id": 3, "name_tk": "Eltip berlende terminal", "name_ru": "Терминал при доставке" },
    "decision_comment": null,
    "stores": [
      {
        "id": 21,
        "status": "pending",
        "subtotal": 200,
        "store": { "id": 3, "name": "Altyn Bazar", "phone": "+99361234567", "logo_url": "..." },
        "items": [
          {
            "id": 44, "listing_id": 108, "title": "Рис длиннозёрный",
            "unit_price": 100, "is_wholesale": false, "qty": 2, "total": 200,
            "photo": "https://.../thumb.webp"
          }
        ]
      }
    ],
    "created_at": "2026-09-02T12:00:00+00:00"
  },
  "message": "Заказ отправлен продавцу. Он свяжется с вами для подтверждения"
}
```

После `201` — **очистить корзину этого магазина** (не всю, если в корзине
остались товары других продавцов) и открыть карточку заказа.

#### `GET /v1/orders?status=pending&page=1&limit=20` — мои заказы

Пагинация обычная (`meta` + `links`). Фильтр `status` необязателен.

#### `GET /v1/orders/{id}` — карточка заказа

Только свой заказ, чужой — `404`.

#### `POST /v1/orders/{id}/cancel` — отменить

Работает, пока `can_cancel == true`. Иначе `422` с текстом «Продавец уже принял
заказ — свяжитесь с ним по телефону».

### Владелец магазина

| Запрос | Что делает |
|---|---|
| `GET /v1/my/store/orders?status=pending&limit=20` | Заказы магазина. `meta.pending` — число для бейджа на вкладке |
| `GET /v1/my/store/orders/{id}` | Карточка части заказа |
| `POST /v1/my/store/orders/{id}/accept` | «Беру заказ»: заказ подтверждён, остатки списаны. Тело: `{ "comment": "..." }` (необязательно) |
| `POST /v1/my/store/orders/{id}/decline` | Отказ, заказ закрыт. Тело: `{ "comment": "Товар закончился" }` |
| `POST /v1/my/store/orders/{id}/complete` | «Отвёз и получил деньги» — последний шаг |

`{id}` здесь — id **части** заказа (`stores[0].id`).

Заказ приходит владельцу **сразу после оформления**, и решение по нему
принимает он: `accept` переводит весь заказ в `approved`, `decline` — в
`rejected`. Кнопки «Принять» / «Отказать» показываем по `can_respond`,
«Доставлено» — по `can_complete`.

Контакты покупателя и адрес приходят вместе с заказом (`buyer`, `delivery`) —
доставку делает сам продавец. Нарисуй блок «Покупатель» с кнопкой «Позвонить»
и адресом доставки.

## Что нужно собрать

### Экраны покупателя

1. **Кнопка «В корзину»** в карточке товара и в ленте — по `is_orderable`.
   Счётчик количества ограничен `stock_qty` (при `null` ограничения нет),
   стартовое значение — `min_order_qty`, если розничной цены нет.
2. **Корзина** — список позиций, сгруппированных по магазинам, изменение
   количества, удаление, предварительная сумма, кнопка «Оформить».
3. **Оформление** — адрес обязателен, остальные поля предзаполнены из профиля
   и редактируемы, поле комментария, **выбор способа оплаты** радиокнопками из
   `payment_methods` магазина плюс вариант «не выбрано» (поле необязательное).
4. **Мои заказы** — список со статусами и номером, фильтр по статусу.
5. **Карточка заказа** — статус, состав, суммы, способ оплаты
   (`payment_method`, при `null` — «обсуждается с продавцом»),
   `decision_comment` при отказе, телефон продавца с кнопкой «Позвонить»,
   кнопка «Отменить» при `can_cancel`.

### Экран владельца магазина

6. **Вкладка «Заказы»** в аккаунте магазина — список с бейджем `meta.pending`,
   карточка заказа с блоком «Покупатель» (имя, «Позвонить», адрес, пожелание)
   и **способом оплаты** — продавец едет за деньгами сам, от способа зависит,
   брать ли сдачу или терминал; кнопки «Принять» и «Отказать» при `can_respond`,
   «Доставлено» при `can_complete`, поле комментария при отказе.
7. **Комиссия платформы** в карточке части заказа: при `commission_percent > 0`
   показать строкой «сумма — комиссия N% = к получению» (`subtotal`,
   `commission`, `payout`), при `0` блок не рисовать. Покупателю комиссию не
   показывать нигде: он платит `subtotal` целиком, ставка удерживается с
   магазина.

## Обработка ошибок

| Код | Где | Что показать |
|---|---|---|
| `422` | `POST /v1/orders` | `errors.items[0]` — уже локализованный текст, показать как есть и подсветить проблемную позицию |
| `422` | `POST /v1/orders` | `errors.payment_method_id` — магазин не принимает такой способ: перечитать магазин и обновить список |
| `422` | отмена заказа | Продавец уже ответил — убрать кнопку отмены, обновить карточку |
| `422` | accept / decline | Ответ уже дан или заказ отменён — обновить карточку |
| `422` | complete | Заказ ещё не принят или уже закрыт — обновить карточку |
| `404` | карточка заказа | Чужой или удалённый заказ |
| `404` | карточка части заказа | Чужой магазин |
| `403` | `POST /v1/orders` | Пользователь заблокирован |
| `429` | любой POST | Лимит частоты, обработать отдельно от `422` |

Причины `422` при оформлении: пустая корзина, **товары разных магазинов**,
товар недоступен, магазин без доставки, нет в наличии, осталось меньше
заказанного, количество меньше минимальной партии, у товара нет цены, попытка
заказать собственный товар.

**Лимиты частоты:** `POST /v1/orders` — 20/мин (помни: корзина из трёх
магазинов = три запроса), отмена и ответы магазина — 30/мин. Счётчик общий на пользователя, а не на эндпоинт: серия лайков (60/мин)
может выбить `429` на оформлении в ту же минуту.

## Push-уведомления

Два новых `type` в payload:

| `type` | `id` | Куда вести |
|---|---|---|
| `order` | id заказа | Карточка заказа покупателя |
| `store_order` | id части заказа | Карточка заказа в магазине |

Пуши приходят: покупателю — решение продавца (принял / отказался) и
«доставлен»; владельцу — новый заказ сразу после оформления и отмена заказа
покупателем. Неизвестный `type` уводит на `/home` — рабочий fallback, но эти
два лучше обработать.

## Порядок работ

1. `is_orderable` в карточке и ленте → кнопка «В корзину».
2. Локальная корзина в SharedPreferences (`keyCart`) + экран корзины,
   **сгруппированный по магазинам**, со своей кнопкой «Оформить» у каждой группы.
3. Экран оформления, `POST /v1/orders` на один магазин, очистка его позиций
   после `201`. Способ оплаты — из `payment_methods` магазина, необязателен.
4. Обработка `422` по `errors.items[0]`.
5. «Мои заказы» + карточка + отмена + телефон продавца.
6. Вкладка «Заказы» у владельца магазина + accept / decline / complete.
7. Deep-link из push: `order` и `store_order`.

---

## Чего делать не нужно

- Не изобретай API корзины — её эндпоинтов нет, корзина локальная
- Не собирай правило доступности заказа сам — есть `is_orderable`
- Не считай свою сумму итоговой — источник истины `total` из ответа сервера
- Не пересчитывай цену старого заказа по текущей карточке товара — в позиции
  лежит снимок `unit_price`
- Не путай id заказа и `stores[].id` в эндпоинтах магазина
- Не рисуй оплату, доставку с ценой, курьера и трекинг — этого в системе нет
- Не собирай корзину из товаров разных магазинов в один заказ — 422
- Не жди подтверждения админа: его в заказе нет вообще, всё решает продавец
- Не подменяй серверные тексты ошибок своими

## Как проверить

В репозитории бэкенда есть Bruno-коллекция, папка `Orders` — девять готовых
запросов с описаниями. Порядок: Auth → «Отправить SMS-код» (код пишется
в `storage/logs/laravel.log` на дев-стенде) → «Подтвердить код», токен
сохранится сам.

Для полного сценария нужен магазин со статусом `approved` и `has_delivery = 1`,
у его товара — цена и статус `approved`. У такого товара в ленте придёт
`is_orderable: true`. Сразу после оформления заказ виден владельцу магазина —
он же его принимает и закрывает доставленным; в админ-панели заказ только
отображается.
