# Промпт для мобильного разработчика (Flutter + Cursor): подключение к API

Скопируй всё, что ниже разделителя, в Cursor (или другого AI-агента) как задачу.
Это общая карта: как приложение разговаривает с сервером и какие правила
логики сервер навязывает. Поля ответов подробно — в
[`BACKEND_API.md`](./BACKEND_API.md), живые примеры каждого запроса — в
Bruno-коллекции `bruno/` в корне репозитория бэкенда. Магазины и заказы
расписаны отдельно: [`FLUTTER_STORES_PROMPT.md`](./FLUTTER_STORES_PROMPT.md),
[`FLUTTER_ORDERS_PROMPT.md`](./FLUTTER_ORDERS_PROMPT.md).

# Задача: подключить приложение Sowda к API сервера

Ты работаешь во Flutter-приложении доски объявлений Sowda (Туркменистан).
Бэкенд — Laravel, мобильное API `/api/v1` готово и покрыто тестами. Нужно,
чтобы каждый экран приложения брал данные с сервера и правильно вёл себя на
всех ответах сервера, включая ошибки. Не придумывай поля и эндпоинты: всё,
чего нет в этом документе, в `BACKEND_API.md` или в Bruno, — спроси.

## 1. Базовые вещи

| | |
|---|---|
| Base URL (прод) | `https://dashoguzsowda.com.tm/api` |
| Base URL (dev) | `http://<IP машины разработчика>:8000/api` — берётся из конфигурации сборки, не хардкодить |
| Префикс | все пути ниже — от `/v1/...` |
| Заголовки на каждом запросе | `Accept: application/json`, `Accept-Language: tk` или `ru`, `Authorization: Bearer {token}` (если токен есть) |
| Именование полей | `snake_case` в запросах и ответах |
| Даты | ISO 8601 (`2026-10-05T12:00:00+00:00`) |
| Деньги | number (манаты), сервер округляет до 2 знаков |

- `Accept-Language` обязателен: от него зависят **все** тексты, которые
  приходят с сервера (`message`, ошибки валидации, названия из справочников
  через `content`). Неизвестный язык → сервер отвечает по-русски. Язык
  пользователь выбирает в онбординге, хранится локально.
- **Гостевого режима нет.** Без токена работают только три эндпоинта:
  `GET /v1/about`, `POST /v1/auth/send-code`, `POST /v1/auth/verify`. Всё
  остальное (лента, баннеры, категории, регионы, новости, магазины…) без
  токена отвечает `401`. Поэтому до входа приложение не запрашивает никакой
  контент — только онбординг, «О нас» и экраны входа.

### Формат ответов

```json
// один объект
{ "data": { ... }, "message": "Success" }

// список с пагинацией
{ "data": [ ... ], "meta": { "current_page": 1, "last_page": 10, "per_page": 20, "total": 200 } }
```

Пагинация везде одинаковая: query `page` (с 1) и `limit` (обычно 1…50,
по умолчанию 20). Бесконечный скролл: грузить следующую страницу, пока
`current_page < last_page`. Некоторые справочники (категории, регионы,
баннеры, история чата) приходят списком без `meta`.

## 2. HTTP-клиент: одна точка входа

Сделай один API-клиент (Dio или http) с интерсепторами — ни один репозиторий
не собирает заголовки сам.

- **Интерсептор запроса** подставляет `Accept`, `Accept-Language` из текущей
  локали и `Authorization`, если токен есть.
- **Токен** хранить в `flutter_secure_storage`, не в SharedPreferences.
- **Интерсептор ответа** превращает ошибки в типизированные исключения
  (`ApiException` с `statusCode`, `message`, `errors`). Тексты ошибок уже
  локализованы сервером — показывать `message` как есть, свои строки нужны
  только для сетевых сбоев.

| Код | Что значит | Что делает приложение |
|---|---|---|
| `401` | Нет токена, истёк или отозван | Стереть токен, сбросить состояние, открыть экран входа. Один обработчик на всё приложение |
| `403` | Нельзя: пользователь заблокирован, исчерпан лимит тарифа, чужой ресурс | Показать `message`. Сервер не отдаёт отдельный код причины — не пытаться разобрать текст. Не разлогинивать |
| `404` | Нет такого или не положено видеть (на модерации, чужое, оптовое для розничного клиента) | Экран/плашка «Не найдено», убрать элемент из локальных списков |
| `422` | Ошибка валидации | `errors` — словарь `поле → [тексты]`: подсветить поля формы; если поля нет на экране (например `items`) — показать `message` |
| `429` | Превышен лимит частоты | Тост с `message`, повторить можно позже. Не ретраить автоматически |
| `500` / `503` | Сбой сервера | Общий тост «Что-то пошло не так», кнопка «Повторить» |
| нет сети / таймаут | — | Свой локализованный текст, кнопка «Повторить» |

Пример `422`:

```json
{ "message": "Поле Телефон обязательно.", "errors": { "phone": ["Поле Телефон обязательно."] } }
```

Лимиты частоты, о которых стоит знать заранее: отправка SMS-кода — 5 в
минуту, подтверждение — 10 в минуту, публикация объявления — 20 в минуту,
ролика — 10 в минуту, сообщение в чат — 30 в минуту, оформление заказа —
20 в минуту, отзыв/жалоба — 10 в минуту. Блокируй кнопку на время запроса,
чтобы не упираться в них двойными нажатиями.

## 3. Запуск, вход и регистрация

Регистрация и вход — **один сценарий** по номеру телефона и SMS-коду.

```
Splash
 ├─ онбординг не пройден (локальный флаг) → Онбординг (язык, тема) → Вход
 ├─ токена нет → Вход
 └─ токен есть → GET /v1/profile
       ├─ 401 → стереть токен → Вход
       ├─ is_profile_complete == false → Регистрация профиля
       └─ иначе → Главная
```

1. `POST /v1/auth/send-code` `{ "phone": "+99361234567" }` → в ответе
   `data.expires_in` (секунд жизни кода, 300) и `data.resend_after`
   (через сколько секунд можно запросить снова, 60) — показать таймер
   «Отправить ещё раз».
2. `POST /v1/auth/verify` `{ "phone", "code", "fcm_token" }` → в ответе
   `data.token`, `data.is_new` (новый пользователь) и `data.user`.
   Сохранить токен. `fcm_token` передать сразу — так устройство начнёт
   получать push.
3. Если `user.is_profile_complete == false` — экран регистрации профиля:
   `PUT /v1/profile` с `name`, `region_id`, `city_id` (+ `district_id`,
   `gender`, `birth_date` по желанию). Профиль полный, когда заданы имя,
   регион и город.
4. `GET /v1/preferences` → `onboarding_completed`. После прохождения
   онбординга на новом устройстве — `PUT /v1/preferences`
   `{ "onboarding_completed": true }`. Язык и тема на сервер не уходят.
5. Выход: `POST /v1/auth/logout` `{ "fcm_token": "<токен этого устройства>" }` —
   токен API отзывается, push на это устройство перестают приходить. Затем
   стереть всё локальное, кроме языка, темы и флага онбординга.

Каждый зарегистрированный пользователь **сразу на бесплатном тарифе** —
`profile.tariff` не бывает пустым.

## 4. Профиль и тариф

- `GET /v1/profile` — профиль, плюс `store` (свой магазин или `null`),
  `tariff`, `tariff_request` (незакрытая заявка на тариф), `stats`,
  `is_premium`, `is_profile_complete`. Перезапрашивать после любого действия,
  которое может их поменять (смена тарифа, создание магазина).
- `PUT /v1/profile` — частичное обновление: слать только изменённые поля.
- `POST /v1/profile/avatar` (multipart, поле `avatar`, jpg/png/webp до 5 МБ),
  `DELETE /v1/profile/avatar`.
- Смена номера: `POST /v1/profile/phone/send-code` `{ "phone" }` →
  `POST /v1/profile/phone/confirm` `{ "phone", "code" }`. Без подтверждения
  номер не меняется.
- `PUT /v1/profile/fcm-token` `{ "fcm_token", "platform": "android"|"ios" }` —
  вызывать при каждом обновлении FCM-токена (`onTokenRefresh`).
- Тарифы:
  - `GET /v1/tariffs` — каталог планов с ценой и правами (`can_have_store`,
    `can_see_wholesale`, лимиты);
  - `GET /v1/profile/tariff` — текущий тариф и остатки лимитов;
  - `PUT /v1/profile/subscription` `{ "tariff_name" }` — **не включает
    платный тариф сразу**. Онлайн-оплаты нет: создаётся заявка, деньги
    пользователь отдаёт администратору лично, тариф включает админ. Показать
    «Заявка отправлена, ожидает оплаты» по `tariff_request`. Бесплатный
    тариф назначается сразу. Одна незакрытая заявка на пользователя.
  - Платный тариф истекает → пользователь переводится на бесплатный, приходит
    push `type: tariff`. Объявления и ролики сверх лимита бесплатного
    получают статус `suspended` (см. ниже).

## 5. Справочники и главная

Справочники грузить после входа и кэшировать на сессию:

| Эндпоинт | Что |
|---|---|
| `GET /v1/categories` | Дерево категорий (3 уровня). Объявление создаётся в **конечной** категории, ролик — в категории **1-го уровня** |
| `GET /v1/regions` | Регионы → города → районы, для форм профиля, объявлений, заказа |
| `GET /v1/banners` | Промо-карусель на главной (уже отфильтрована по датам показа) |
| `GET /v1/complaint-reasons` | Причины для формы жалобы |
| `GET /v1/news?type=regular\|ad`, `GET /v1/news/{id}` | Новости; у рекламных — `ad_link`, куда вести (см. BACKEND_API §13) |
| `GET /v1/about` | «О нас»: HTML в `content` на языке `Accept-Language` (рендерить как HTML). Работает без токена |

## 6. Объявления

**Лента** `GET /v1/listings`: `search`, `category_id` (родитель включает всё
поддерево), `region_id`, `city_id`, `type` (`goods`|`services`),
`price_min`, `price_max`, `sort` (`latest` — по умолчанию, поднятые сверху |
`price_asc` | `price_desc` | `nearest` — тогда обязательны `lat`, `lng`),
`page`, `limit`.

**Карточка** `GET /v1/listings/{id}` — сервер сам считает просмотр (кроме
автора). Отзывы об объявлении — `GET /v1/listings/{id}/reviews`
(`sort`: `latest`|`rating_desc`|`rating_asc`).

**Свои** `GET /v1/listings/my?status=pending|approved|rejected|suspended`.

**Создание** `POST /v1/listings` — `multipart/form-data`:
`title`, `description`, `type`, `category_id` (конечная), `region_id`,
`city_id`, `district_id?`, `price?`, `phone?` (`+993XXXXXXXX`), `tags[]?`
(до 10 по 30 символов), `location[lat]?` + `location[lng]?`,
`photos[]` (1–8 фото jpg/png/webp, до 15 МБ каждое). Товары магазина —
плюс `wholesale_price?`, `min_order_qty?`, `stock_qty?` (см. промпт
магазинов).

- Если у пользователя есть магазин, объявление само становится товаром
  магазина и берёт его адрес — регион/город из формы сервер заменит.
- Лимит тарифа исчерпан → `403` с текстом про лимит: предложить перейти на
  экран тарифов.
- Фото сервер обрабатывает в фоне (очередь `media`): сразу после создания
  ссылки на фото могут ещё обновиться — не кэшировать их навсегда, брать из
  ответа при каждом открытии карточки.

**Правка** `POST /v1/listings/{id}` (именно POST — multipart PUT PHP не
разбирает), те же поля. Правка отправляет объявление на повторную модерацию.
**Удаление** `DELETE /v1/listings/{id}`. **Поднять** `POST /v1/listings/{id}/boost`
— ограничено интервалом и лимитом тарифа, отказ приходит `422`/`403` с
текстом.

**Статусы модерации** — показывать плашкой в «Моих объявлениях»:

| `status` | Что показать |
|---|---|
| `pending` | «На проверке» |
| `approved` | опубликовано |
| `rejected` | «Отклонено» + причина из `rejection_reason`, кнопка «Исправить» |
| `suspended` | «Скрыто: превышен лимит тарифа» + кнопка «Продлить тариф». Правка возможна, только если в лимите есть место, иначе `403` |

В публичной выдаче приходят только `approved`. Не фильтруй ничего на
клиенте — сервер уже отдал ровно то, что этому пользователю можно видеть
(включая опт, см. §9).

## 7. Ролики (shorts)

- Лента `GET /v1/videos`: `search` (по заголовку), `category_id` (1-й
  уровень), `tag`, `page`, `limit`. Карточка `GET /v1/videos/{id}`.
- Просмотр `POST /v1/videos/{id}/view` — вызывать, когда ролик реально начал
  играть в ленте. Лайк — `POST /v1/videos/{id}/like` (переключатель).
- Свои `GET /v1/videos/my?status=...`, удаление `DELETE /v1/videos/{id}`.
- Длительность — **до 60 секунд**, категория 1-го уровня обязательна.

**Загрузка.** Маленький файл (до 100 МБ) — одним запросом
`POST /v1/videos` multipart: `video`, `title`, `category_id`, `tags[]?`.
Для больших и для ненадёжной сети — по частям:

1. `POST /v1/videos/upload/init` `{ title, category_id, tags?, filename,
   total_size }` → `data.upload_id`, `data.chunk_size`, `data.max_bytes`.
   Квота тарифа проверяется сразу (`403`), до передачи байтов.
2. `POST /v1/videos/upload/{upload_id}/chunk?index=N` — тело запроса —
   **сырые байты** части (`Content-Type: application/octet-stream`), части
   строго по порядку с 0. Размер части — `chunk_size`. Читать файл кусками,
   не грузить целиком в память.
3. `POST /v1/videos/upload/{upload_id}/complete` → `201` с роликом
   (`status: pending`, сжатие идёт в фоне). Ошибки: `422` — файл битый или
   длиннее 60 секунд, `404` — сессия загрузки истекла (начать заново).
4. Отмена — `DELETE /v1/videos/upload/{upload_id}`.

Показывай прогресс по отправленным частям; при обрыве сети повторяй ту же
часть с тем же `index`.

## 8. Избранное, отзывы, жалобы, поиск

- Избранное: `GET /v1/favorites`, `POST /v1/favorites` `{ listing_id }`,
  `DELETE /v1/favorites/{listing_id}`. В ленте и карточке есть
  `is_favorite` — сердечко рисовать по нему.
- Отзывы: `POST /v1/reviews` `{ text, rating?, listing_id }` либо
  `{ text, rating?, target_user_id }` (отзыв о продавце). Отзыв уходит на
  модерацию и не появляется сразу. Свои — `GET /v1/reviews/my`, правка
  `PUT /v1/reviews/{id}` (снова на модерацию), удаление
  `DELETE /v1/reviews/{id}`. Отзывы о продавце — `GET /v1/users/{id}/reviews`.
- Жалоба: `POST /v1/complaints` `{ listing_id, complaint_reason_id, text? }`.
- Поиск: популярные запросы `GET /v1/search/popular`; история —
  `GET/POST/DELETE /v1/search/recent` (`POST` с `{ "query" }` после каждого
  поиска, `DELETE` — очистить). Локальную «историю гостя» не делать.
- Заблокированный пользователь не может публиковать, лайкать, оставлять
  отзывы, жалобы и заказы — сервер отвечает `403` с текстом блокировки.
  Читать контент он может.

## 9. Магазины и опт

Вся логика — в [`FLUTTER_STORES_PROMPT.md`](./FLUTTER_STORES_PROMPT.md). Коротко:

- Публичные: `GET /v1/stores/popular`, `GET /v1/stores` (фильтры `search`,
  `region_id`, `city_id`, `district_id`, `category_id`,
  `type=retail|wholesale`, `has_delivery`), `GET /v1/stores/{id}`,
  `GET /v1/stores/{id}/listings` (`search`, `category_id`,
  `trade=retail|wholesale`, `in_stock`, `sort`).
- Свой магазин: `GET /v1/my/store`, `POST /v1/my/store` (создать),
  `POST /v1/my/store` + `_method=PUT` (правка с файлами). Только на тарифе с
  `can_have_store`. Магазин модерируется; правка названия, описания, адреса
  или логотипа возвращает его на проверку.
- Объявления пользователя, поданные **до** открытия магазина, при создании
  магазина сами становятся его товарами.
- **Опт видят только тарифы с `can_see_wholesale`** (флаг в
  `profile.tariff`). Вкладку «Опт/Розница» показывать по нему; оптовые цены и
  чисто оптовые товары сервер остальным просто не отдаёт.

## 10. Заказы

Вся логика — в [`FLUTTER_ORDERS_PROMPT.md`](./FLUTTER_ORDERS_PROMPT.md). Коротко:

- Корзина живёт **на устройстве**, API корзины нет. Кнопка «В корзину» —
  только у объявлений с `is_orderable == true`.
- `POST /v1/orders` — один заказ на один магазин: корзину с товарами разных
  магазинов приложение режет и оформляет несколькими запросами.
- **Геолокация покупателя:** при оформлении запроси разрешение на геолокацию
  и отправь `lat` + `lng` (только парой). Отказ в доступе — не ошибка, поля
  просто не слать; `address` обязателен всегда. Продавец получает точку в
  `delivery.location` и открывает её в картах.
- `payment_method_id` — из способов оплаты именно этого магазина, необязателен.
- Мои заказы `GET /v1/orders?status=...`, карточка `GET /v1/orders/{id}`,
  отмена `POST /v1/orders/{id}/cancel` (только пока продавец не ответил,
  флаг `can_cancel`).
- Владелец магазина: `GET /v1/my/store/orders?status=…&q=…`, карточка,
  `accept` / `decline` (`{ comment? }`) / `complete`. Кнопки — по флагам
  `can_respond` и `can_complete`.

## 11. Чат с поддержкой (REST + WebSocket)

Один диалог пользователя с администрацией, чата между пользователями нет.

- `GET /v1/chat` — вся переписка по возрастанию даты: `id`, `sender`
  (`user`|`admin`), `text`, `is_read`, `created_at`.
- `POST /v1/chat` `{ "text" }` — отправить сообщение.
- `PATCH /v1/chat/read` — пометить ответы админа прочитанными (вызывать при
  открытии чата).

**Realtime** — Laravel Reverb, протокол Pusher. Пакет на стороне Flutter —
клиент Pusher-протокола со своим хостом, например `dart_pusher_channels`
(официальный `pusher_channels_flutter` завязан на облако Pusher и свой хост
не поддерживает).

| | |
|---|---|
| Хост / порт | те же, что у API: прод `wss://dashoguzsowda.com.tm:443`, dev `ws://<IP>:8000` (nginx проксирует путь `/app` на Reverb) |
| Путь подключения | `/app/{REVERB_APP_KEY}?protocol=7` — ключ выдаёт команда бэкенда, он не секретный |
| Авторизация канала | `POST {base_url}/broadcasting/auth` (то есть `/api/broadcasting/auth`) с `Authorization: Bearer {token}`, тело `socket_id`, `channel_name` → `{ "auth": "..." }` |
| Канал | `private-chat.{user_id}` — только свой, чужой → `403` |
| Событие `new-message` | новое сообщение: `{ id, user_id, text, sender, is_read, created_at }` — добавить в список, если такого `id` ещё нет |
| Событие `messages-read` | собеседник прочитал: `{ user_id, sender }` — пометить прочитанными сообщения этого `sender` |

Подключаться к сокету только на экране чата (или при активном приложении),
отключаться при уходе в фон. При переподключении — перезапросить
`GET /v1/chat`, чтобы не потерять сообщения, пришедшие без сокета.

## 12. Push-уведомления (FCM)

- Токен отправлять в `auth/verify` и `PUT /v1/profile/fcm-token` (при каждом
  обновлении), удалять — в `auth/logout`. Устройств у пользователя может быть
  несколько.
- Данные — в `data`, все значения строки: `{ "type": "...", "id": "..." }`
  (для `external`/`url` — `"url"` вместо `"id"`).

| `type` | Куда открыть |
|---|---|
| `listing` | карточка объявления (одобрено/отклонено) |
| `store` | свой магазин (модерация) |
| `tariff` | экран тарифа (заявка решена, тариф истёк) |
| `order` | карточка заказа покупателя |
| `store_order` | заказ магазина (`id` — часть заказа: `/v1/my/store/orders/{id}`) |
| `chat` | чат |
| `news` | новость |
| `external` / `url` | открыть `url` во внешнем браузере |
| неизвестный или без `id` | `/home` — штатный fallback, не ошибка |

Нажатие на push при закрытом приложении: сначала обычный splash-поток (токен,
профиль), потом переход по `type`.

## 13. Что хранится только на устройстве

Язык, тема, флаг онбординга (плюс синхронизация через `/v1/preferences`),
переключатель push, корзина. Токен — в secure storage. Остальное с сервера,
кэш — только для скорости, источник правды — API.

## 15. Как проверить, что готово

- Без токена приложение не делает ни одного запроса, кроме `about` и
  `auth/*`; `401` на любом экране выкидывает на вход ровно один раз.
- Переключение языка меняет тексты ошибок и названия из справочников со
  следующего запроса.
- Каждая форма подсвечивает поля по `errors` из `422`.
- `403` по лимиту тарифа ведёт на экран тарифов, по блокировке — показывает
  текст и не разлогинивает.
- Объявление в `rejected` показывает причину, в `suspended` — кнопку тарифа.
- Ролик на 200 МБ загружается по частям с прогрессом и переживает обрыв сети.
- Сообщение админа в чате появляется без перезагрузки экрана; push каждого
  типа открывает нужный экран.
- Перед сдачей прогони сценарии против Bruno-коллекции: каждый запрос в ней —
  рабочий пример тела и ответа.
